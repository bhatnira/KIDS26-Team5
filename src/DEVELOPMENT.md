# Development & Release Guide

This project is a Go backend (single binary with `web` / `monitor` subcommands)
plus a Vue 3 frontend in `web_src/`. This document describes the standard dev,
build, and release process.

## Source of truth: the Makefile

All build commands live in the **Makefile**. Everything else delegates to it so
the same command always does the same thing:

- **Justfile** — thin wrapper; each recipe calls the matching `make` target.
- **Dockerfile** — calls `make frontend` and `make server-embed`.
- **.goreleaser.yaml** — its `before` hook runs `make frontend`; its build flags
  mirror the Makefile's `EMBED_TAGS` and version injection.

Run `make help` (or `just`) to list targets.

### Build configuration

| Knob | Default | Meaning |
|------|---------|---------|
| `VERSION` | `git describe --tags --always --dirty` | injected into `main.Version` (server) and `main.version` (CLI) |
| `EMBED_TAGS` | `embed,timetzdata` | Go build tags for the self-contained build: `embed` bakes in `web_src/dist`; `timetzdata` bakes in the tz database |

Override on the command line, e.g. `make server-embed VERSION=v1.2.3`.

## Two build modes

The frontend is embedded only when the `embed` build tag is set:

- **Plain (`make server`)** — no embedded UI, no frontend build needed. Use this
  for local backend dev; serve the UI separately with the Vite dev server.
- **Embedded (`make server-embed`)** — bakes the compiled `web_src/dist` into the
  binary via `//go:embed`. Requires the frontend to be built first.

> Email templates (`templates/`) are always embedded, regardless of build tag.

## Local development

```bash
# Terminal 1 — backend (debug mode, no embedded UI)
make dev                 # runs: go run . web

# Terminal 2 — frontend with hot-module reload
cd web_src && pnpm install && pnpm run dev   # Vite dev server on :9999
```

The browser hits the Vite dev server (HMR); API calls go to the backend. The
`embed` tag is **not** used in dev, so this loop is unaffected by the embedding.

Other common targets:

```bash
make lint        # golangci-lint run ./...
make test        # go test -race -cover ./...
make fmt         # gofmt + goimports
make swagger     # regenerate docs/swagger (commit the result)
make tidy        # go mod tidy && verify
```

## Producing a self-contained binary

```bash
make build-embed   # frontend + embedded server + CLI → bin/
./bin/antelope web
```

`bin/antelope` now serves both the API and the frontend on one port (`:8086`),
and reads email templates from the embedded FS — no `web_src/` or `templates/`
directory needs to be present at runtime.

## Building the container image

The image is server-only (the CLI ships as a release binary). The multi-stage
`Dockerfile` builds the frontend on the native platform, then cross-builds the
backend, both via `make`:

```bash
docker build -t antelope .
docker build --build-arg VERSION=v1.2.3 -t antelope .
```

## CI / CD (GitHub Actions, GitOps)

Workflows live in `.github/workflows/`:

| Workflow | Trigger | What it does |
|----------|---------|--------------|
| `ci.yml` | PRs + push to `main` | `golangci-lint`, `make test`, and `make build-embed` (proves the full embed build compiles) |
| `release.yml` | tags `v*` | `goreleaser release --clean` → cross-platform binaries (linux/windows/darwin × amd64/arm64) attached to a GitHub Release |
| `docker.yml` | tags `v*` + push to `main` | `buildx` multi-arch image (`linux/amd64,linux/arm64`) pushed to `ghcr.io/<owner>/antelope` |

### Cutting a release

```bash
git tag v1.2.3
git push origin v1.2.3
```

This fires both `release.yml` (binaries) and `docker.yml` (image). The tag drives
the version stamped into binaries and image tags.

Local dry run before tagging:

```bash
goreleaser release --snapshot --clean   # build artifacts without publishing
goreleaser check                        # validate .goreleaser.yaml
```

## Notes

- `docs/swagger/` is generated by `make swagger` and **committed** — the backend
  imports it (`antelope/docs/swagger`) and the Docker build relies on it being
  present. Re-run `make swagger` and commit after changing handler annotations.
- The CI lint job uses `golangci-lint-action` with `version: latest`; pin it to a
  specific `v2.x` for fully reproducible runs.
- Pushing images to GHCR uses the built-in `GITHUB_TOKEN`; no extra secret is
  required. The first push may create a private package — make it public in the
  repo's package settings if you want anonymous pulls.
